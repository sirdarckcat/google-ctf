Watch a cipher break.

Two techniques — differential and integral cryptanalysis — run live in your browser against a real 16-round block cipher. Every number on this page is computed as you read it, by a WebAssembly build of the same code that recovers the key.

01

The cipher, in one round

Two 32-bit halves, lo and hi. Sixteen rounds. Each round looks up one byte of lo in a fixed public table (an S-box), XORs the result into hi, rotates, and swaps:

hi = hi ⊕ SB[ lo & 0xff ] ← only ONE byte is looked up lo = ror(lo, ROT[r]) ROT = 16,16,8,8,16,16,24,24 lo, hi = hi, lo

The 64-bit key is XORed in only three times — before, between and after the two groups of eight rounds. That single fact (“one byte per round”) is why you can follow an attack through this cipher by eye.

02

Differential: follow a difference

Take two plaintexts that differ in one byte. Because the key is only XORed in, it cancels out of any difference — (P⊕K)⊕(P'⊕K) = P⊕P' — so a difference moves through the cipher in a way you can predict without knowing the key.

Each round the S-box is either active (the byte feeding it differs, so it injects an unpredictable difference) or inactive (that byte is identical, so it contributes nothing and the difference sails through untouched). The whole game is keeping S-boxes inactive.

Difference trail — 16 roundschange the byte and watch

nonzero byte differs 00 byte identical active S-box sees a difference inactive free round

Put the difference in byte 6 and it rides seven rounds free — a lone byte wandering around while every S-box stays inactive — then detonates at round 7. Try byte 3: it is the lookup byte, so it is active immediately. Every position gives a different number of free rounds, and byte 6 is the best there is.

This is the single most valuable fact about this cipher, and both attacks on this page are built on it.
03

Where the luck lives

After round 7 the difference has spread. To keep going we need it to cancel — an S-box output difference landing on a byte that already differs, the two XORing to zero and making a later round inactive again. How often does that happen? Don't guess. Measure.

P(S-box inactive) per roundidle

Three regimes, and the middle one is the interesting part:

Rounds 0–6 — always inactive. The free ride. Not probability; certainty.

Rounds 7–9 — never inactive. Exactly zero, however many pairs you run. Here the difference has just landed in a half that had no difference, so cancelling would require the S-box to output a zero difference byte. This S-box is built from four independent byte permutations, so it never does — checking…

Rounds 10+ — about 1 in 256. Now the difference lives in both halves, so cancelling no longer needs a zero output difference; it just needs the S-box output byte to equal the difference already sitting there. One byte matching one byte.

The trap: “the S-box never outputs a zero difference” is true, and it does not mean “differences can never cancel”. Cancellation happens against a nonzero difference. Confusing the two makes you declare a cipher safe when it isn't — a mistake made, and caught, while writing this.

The real attack asks for rounds 12 and 14 to be inactive: about 1/256 × 1/256 ≈ 2⁻¹⁶. So ~196,000 pairs buy you about three usable ones, and that is where the attack's data cost comes from.

04

Integral: stop hoping, start proving

Same structural fact, spent differently. Instead of two texts, take a whole set: one byte running through all 256 values, everything else fixed. Now track four labels per byte —

A  saturated — hits all 256 values C  constant B  balanced — XORs to zero ?  unknown

Two rules do all the work. XOR is linear, so balance survives it — but A ⊕ A = B, saturation decays into mere balance. And the S-box: a constant in gives a constant out, a saturated byte in gives saturated bytes out (it's a bijection) — but a merely balanced byte in gives nothing, because a sum tells you nothing about individual values and the S-box needs values.

Integral propagation — measured, not predicted…

Read it downward. A lone A drifts for seven rounds — the same free ride, now costing no probability at all. At round 7 it enters the S-box and spreads. Then A⊕A collapses saturation into balance, and the moment a B is the byte feeding the S-box, everything downstream turns to ?.

Now add byte 2 as a second saturated byte (65,536 texts). The property reaches a round deeper — and that extra round is exactly what the real key recovery needs. Of all 28 possible pairs, only {2,6} gets there, because 6 and 2 are the two positions that take longest to reach an S-box.

Differential needs 2⁻¹⁶ luck and statistics. Integral needs none — it is true for every key, every time. You pay in queries instead: a whole set, not a pair.
05

Take the key

A property isn't a key. The bridge: guess a little key, undo a little cipher, check whether the property survives. The rounds contain no key here — it lives only in the final whitening — so once you guess those few bytes, running rounds backwards is public arithmetic.

Right guess ⇒ the bytes really are balanced, guaranteed. Wrong guess ⇒ balanced only by luck, 1 in 256 per byte checked. Below is the real thing, on a cipher shortened so the naive “try every guess” fits in a browser tab.

Each extra round you unwind costs exactly one more key byte — a factor of 256 — because only one byte feeds each S-box:

The full 16-round cipher needs all four bytes — 2³², far too many to enumerate. The fix isn't a bigger computer, it's a better search: the balance test is an XOR-correlation, and a Walsh–Hadamard transform evaluates it for all 2²⁴ candidate keys at once, the way an FFT does for ordinary convolution. That turns the real attack into 65,536 chosen plaintexts and about five minutes — three times less data than the intended differential attack, with a unique answer instead of a majority vote.

What you just ran

A 14 KB WebAssembly module — the cipher, difference tracing, the measurement loop, integral labelling and the key recovery above — compiled with clang --target=wasm32 -msimd128 from the same C that solves the challenge. Nothing is precomputed or faked.

Speed is why this is possible in a tab. Two million difference pairs take about 240 ms here; the identical measurement in NumPy takes 4.9 s — a 20× gap, because NumPy has to materialise sixteen intermediate arrays where WebAssembly keeps one byte in a register. On the heavier Walsh–Hadamard kernel the gap narrows to about 5×, landing within 1.6× of native C.

The full 16-round key recovery is the one thing not run here: it needs 65,536 chosen plaintexts and about five minutes of native C. Everything leading up to it is above.

Full write-ups, the verified reference implementation, the Python labs and the complete key-recovery solver live in the crypto-sphinx solution directory — DIFFERENTIAL.md, INTEGRAL.md, difflab.py, intlab.py, solve_integral_opt.c.

The cipher is Ralph Merkle's Khafre (1989), published for study. Keys here are generated in your browser and thrown away.
